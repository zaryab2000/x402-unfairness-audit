# Methodology

How the numbers in the report were produced, what was assumed, and where the
evidence does not reach. Read this before disputing a figure — several
objections are pre-answered here, and one real limitation is disclosed that a
reader would otherwise have to find on their own.

## 1. The snapshot

`data/raw-data.json` is a frozen extract of a merchant catalog index, collected
at **2026-07-25T11:41:43Z**. It contains 1,212 catalogued merchants, of which
1,132 carry a stored score breakdown; 26,256 resources; and 13 categories.

It is never regenerated by anything in this repo. No script writes to it. It is
evidence, and re-collecting it would produce a different dataset — the live
catalog moves continuously — which would silently invalidate every figure in the
report. If you want fresh data, that is a new study, not a re-run of this one.

Fields were not cleaned, re-sorted, or trimmed. What the collector wrote is what
is published, including fields no analysis reads.

## 2. Category selection

Four categories are analysed: **Crypto & DeFi** (303 merchants), **AI & Agents**
(128), **Data & Enrichment** (34) and **Finance & Markets** (31) — 496 merchants
in total.

"Other" (636 merchants) is excluded. It is the uncategorised fallback bucket, so
a concentration measure over it describes the bucket's heterogeneity, not a
market's structure. Excluding it removes more than half the catalog, which is
worth stating plainly: the findings describe the four named categories, not the
x402 ecosystem in aggregate.

Finance & Markets (31 merchants) is thin. It is retained as the smallest
coherent category, and its Gini (0.7809) is the lowest of the four — it is the
weakest instance of the pattern, not a cherry-picked strong one.

**The author's own service appears in the audited catalog.** It is listed like
any other merchant, sits in the excluded "Other" bucket, and therefore
contributes to no analysed statistic in this study. It receives no special
handling: its rows were left in the snapshot exactly as collected.

## 3. The scoring formula

### Provenance

`src/ranker.ts` is the scoring implementation **as of the snapshot date
(commit `5b327e0`, 2026-07-25)**. The production formula has since evolved: the
listing-quality component was later rewritten to gate description scoring on
composite quality (keyword density, category-keyword presence, structural
specificity, fluff detection), to weigh service-name specificity and tag
taxonomy relevance, and to add an icon-presence bonus, changing the
normalisation constant from 3.6 to 3.75.

This matters beyond bookkeeping. Verifying against the current implementation
reproduces the snapshot's listing quality for **21 of 1,132** merchants; the
snapshot-date implementation reproduces **1,132 of 1,132**. Ranking formulas
change under operators' feet, and a merchant optimising against last quarter's
weights is optimising against a formula that no longer exists. The audit is
pinned to the formula that produced the data.

### The formula

```
score = 0.40·volume
      + 0.25·buyerDiversity
      + 0.05·reliability
      + 0.15·listingQuality
      + 0.15·recency
```

Components, each normalised to [0, 1]:

- **volume** — `0.5·logNorm(txCount30d) + 0.5·logNorm(volume30d)`, log-scaled
  (cap 1,000,000) so heavy tails do not dominate linearly.
- **buyerDiversity** — `logNorm(buyers30d)` with cap 10,000.
- **reliability** — a constant `0.5` for every merchant. No external source
  exposes per-service health. Verified: all 1,132 rows carry exactly 0.5, so
  this component contributes nothing to any ranking difference and its share of
  every gap decomposition is exactly 0.
- **listingQuality** — mean over the merchant's resources of: input schema
  (+1.0), output example (+1.0), description length tier (>150 chars +0.8,
  >50 +0.4), service name present (+0.5), tag count (3–5 tags +0.3, otherwise
  ≥1 +0.1); normalised by 3.6 and clamped to 1.
- **recency** — a decay ladder on the most recent activity timestamp:
  <1 day 1.0, <7 days 0.8, <30 days 0.5, <90 days 0.2, else 0.

The weights are the one place the formula encodes a judgement call, which is why
they are exposed as a single editable constant. See the README's "How to
disagree".

### The reference clock

The production code called `Date.now()` for recency. That is right for a live
index and wrong for reproduction: it makes output depend on the day you run it,
so the same input yields different scores on different days. Verified: replaying
with a live clock reproduces recency for 21 of 1,132 merchants, versus 1,127
when anchored.

This repo anchors recency to the snapshot's own `collectedAt`. Live clocks break
determinism; the snapshot timestamp is the only defensible zero point for a
frozen dataset.

## 4. Equivalence test, and a known reproduction gap

`npm run verify` recomputes all five score components for every merchant from
raw snapshot fields and compares them against the stored breakdown. Result:

| component | exact matches |
|---|---|
| volumeSignal | 1,132 / 1,132 |
| buyerDiversity | 1,132 / 1,132 |
| reliability | 1,132 / 1,132 |
| listingQuality | 1,132 / 1,132 |
| **recency** | **1,127 / 1,132** |

Four components reproduce exactly for every merchant. Recency reproduces for
1,127.

**Cause of the five.** The production formula read a *per-resource*
`lastUpdated` alongside `lastCalledAt`. The collector that wrote the snapshot
did not serialize that field — it kept only a merchant-level `lastUpdated`. For
five merchants the per-resource value was the more recent of the two, so the
reproduction lands one rung down the decay ladder (0.8 instead of 1.0). The
missing input is **not recoverable from published artifacts**. This is
snapshot lossiness, not a discrepancy between the published formula and the one
that produced the numbers.

The five, enumerated so the shortfall is auditable rather than a bare count:

| merchant id | category | stored rank |
|---|---|---|
| `3e834ed9-2ebf-481b-98ad-5beac467c6cc` | Crypto & DeFi | 152 |
| `a715d8fb-72fd-4d75-842f-ff25ef716f82` | Crypto & DeFi | 127 |
| `8a0208e0-73a3-45fb-b832-f5a8688ba043` | AI & Agents | 50 |
| `743b758a-cc36-456c-8f6f-f531f5a1e9c8` | AI & Agents | 53 |
| `e8bfc7bd-2275-4dc3-b647-4a28a41bb3ca` | Data & Enrichment | 26 |

**Checked: no cited figure depends on them.** None of the four merchants named
in the report (basescout-feed, Business Change Intelligence API, Open Source
Filings, StableEnrich) is in this set. The recency delta is 0.2 at weight 0.15,
so each affected merchant's score moves by 0.03. Re-ranking each category with
corrected recency leaves every category's **top-3 membership and top-3 mean
score unchanged**, so no cold-start ceiling gap moves. Data & Enrichment Q1 and
Q2 quartile membership is unchanged; the merchant at rank 26 would move to 33,
crossing the Q3/Q4 boundary and swapping those two quartiles' mean description
lengths (259.0/224.4 → 226.0/266.9). The report's Pass 2 table is cut on the
**stored** `rankPosition` — the ranking the index actually assigned and the one
merchants actually experienced — so the published figures are the correct ones
to cite. The corrected-recency ordering is a sensitivity variant, noted here
rather than substituted.

## 5. Pass 1 — concentration and decomposition

`scripts/analyze.ts`. Gini and HHI are computed over 30-day transaction counts
per category. Quartiles are cut by `rankPosition` ascending, with
`qSize = ceil(n/4)`, so the final quartile absorbs the remainder and can be
smaller than the others (Data & Enrichment: 9/9/9/7).

Gap decomposition attributes the Q1−Q4 mean-score difference to components:
`share_c = (Q1_c − Q4_c) × weight_c / gap`. Shares are reported to four
decimals; because reliability is constant its share is exactly 0 in every
category.

The cold-start ceiling is the maximum score a merchant with no transaction
history can reach: `0.05×0.5 + 0.15×1.0 + 0.15×1.0 = 0.3250`, with volume and
buyerDiversity necessarily 0. It depends only on the weights, so it is identical
across categories.

## 6. Pass 2 — the formula-independent re-cut

`scripts/recut.ts`. Pass 1 can only speak in the formula's own terms. Pass 2
sorts merchants by the rank the index assigned, then measures four raw fields
nobody scored: `hasInputSchema`, `hasOutputExample`, `descriptionLength`,
`tagCount`. If the top quartile were winning on documentation, it would appear
here without any weights involved.

Quartile boundaries are **read from** `data/analysis-results.json`, not
recomputed, so the cut aligns with Pass 1 by construction.

"One merchant, one listing" is itself a choice, and the choice could flatter the
result — so all three defensible rules are emitted:

- **primary** — the merchant's first resource (the figures cited in the report)
- **pooled** — every resource, pooled (multi-listing merchants weigh more)
- **max** — one row per merchant, best value per field

The direction of every axis holds under all three rules; magnitudes shift. In
Data & Enrichment, the bottom quartile has more tags and longer descriptions
than the top under all three, and a lower output-example rate under all three.
`verify.ts` asserts this agreement rather than asking the reader to trust it.

## 7. Known limitations

- **Market scale.** Total 30-day volume across the four analysed categories is
  ~$52,415. Concentration measures over a market this small are real but
  fragile: a handful of merchants moves them. These are early-market findings.
- **Reliability is inert.** At a constant 0.5 the component cannot differentiate
  anyone. Any claim about its 0.05 weight is a claim about a placeholder.
- **Single-query probe design.** The CDP probes used one representative query
  per category. A different phrasing would surface a different result set;
  the probes evidence that a specific reasonable query buries specific
  merchants, not a general claim about all queries.
- **No forward projection.** Everything here describes one instant,
  2026-07-25. Nothing forecasts how concentration evolves.
- **Excluded majority.** 636 of 1,212 merchants sit in "Other" and are outside
  the analysis entirely.
- **Correlation, not causation.** The data shows documentation quality does not
  track rank position. It does not establish that improving documentation would
  fail to help a specific merchant.

## 7a. One edit to a frozen artifact, disclosed

`data/cdp-probes.json` had four annotation keys renamed before publication:
`decipherRank` → `referenceRank`, `decipherScore` → `referenceScore`,
`decipherListingQ` → `referenceListingQ`, `decipherTxCount30d` →
`referenceTxCount30d` (132 keys in total).

These are labels this study's serializer wrote when recording each probe result,
not data the probed endpoint returned. The endpoint's response — result
positions, counts and search method — is the evidence and is untouched; every
value in the file is byte-identical to the 2026-07-25 run. Renaming our own
column headings is not editing evidence, and it keeps the artifact readable
without a product name in it.

The same rule is why the four merchant URLs in `data/raw-data.json` that point
at the author's service were **not** touched: those are catalog content returned
by a third party, so changing them would be falsifying evidence.

## 8. External figures

The ERC-8004 figures cited in the report (~34,000 registrations, 224 live
endpoints; YS Hwang, ETHGlobal NY, June 2026) are **reported by a third party**
and are not measured here. They appear in `claims.json` marked
`"source": "external"`, and `verify.ts` labels them as unverified rather than
passing them silently.

## 9. Reproducing

```bash
npm install
npm run all      # analyze -> recut -> verify
```

No configuration, no database, no network. `npm run analyze` regenerates
`data/analysis-results.json` byte-for-byte identically to the committed copy;
re-running any script produces identical output, since no timestamps, random
seeds or locale-dependent sorting reach the emitted JSON.

`npm run probe` is the exception: it is optional, it touches the network, and it
is non-deterministic by nature. See the README.
