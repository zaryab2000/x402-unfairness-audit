# Methodology

How the numbers in the report were produced, what was assumed, and where the
evidence does not reach. Read this before disputing a figure — several
objections are pre-answered here, and the limitations are disclosed rather than
left for a reader to find.

## 1. The snapshot

`data/raw-data.json` is a frozen extract of a merchant catalog index, collected
at **2026-09-09T08:09:16.700Z**. It contains 2,252 catalogued merchants, every
one of which carries a stored score breakdown; 42,201 resources; and 13
categories.

It is never regenerated by anything in this repo. No script writes to it. It is
evidence, and re-collecting it would produce a different dataset — the live
catalog moves continuously — which would silently invalidate every figure in the
report. If you want fresh data, that is a new study, not a re-run of this one.

Fields were not cleaned, re-sorted, or trimmed. What the collector wrote is what
is published, including fields no analysis reads.

## 2. Category selection

Four categories are analysed: **Crypto & DeFi** (497 merchants), **AI & Agents**
(194), **Data & Enrichment** (91) and **Finance & Markets** (57) — 839 merchants
in total.

"Other" (1,256 merchants) is excluded. It is the uncategorised fallback bucket,
so a concentration measure over it describes the bucket's heterogeneity, not a
market's structure. Excluding it removes more than half the catalog, which is
worth stating plainly: the findings describe the four named categories, not the
x402 ecosystem in aggregate.

Finance & Markets (57 merchants) is thin. It is retained as the smallest
coherent category, and its Gini (0.7371) is the lowest of the four — it is the
weakest instance of the pattern, not a cherry-picked strong one.

**The author's own service appears in the audited catalog.** It is listed like
any other merchant, sits in the excluded "Other" bucket at rank 570 with three
settled transactions, and therefore contributes to no analysed statistic in this
study. It receives no special handling: its rows were left in the snapshot
exactly as collected, and the four resource URLs that identify it — on
`decipher-ranker.vercel.app` and `decipherranker.com` — were not touched.

No merchant in any of the four analysed categories is operated by the author.

## 3. The scoring formula

### Provenance

`src/ranker.ts` is the scoring implementation **as of the snapshot date (commit
`eca0195`, 2026-09-09)** — the version that actually produced the scores stored
in the snapshot. Unlike the July edition of this study, the vendored copy is not
a historical pin: it is current production at collection time.

The listing-quality component is no longer a count of present fields. It grades
them: description scoring is gated on a composite quality score (keyword
density, category-keyword presence, structural specificity, fluff detection),
service-name specificity and tag-taxonomy relevance are weighed, and an
icon-presence bonus was added. The normalisation constant is **3.75**.

Because that component now reads a category taxonomy and three scoring helpers,
`src/ranker.ts` alone no longer describes the formula. Four further modules are
vendored from the same commit and are part of the published evidence:
`src/taxonomy.ts`, `src/description-quality.ts`, `src/tag-quality.ts` and
`src/service-name-quality.ts`.

### The formula

```
score = 0.40·volume
      + 0.25·buyerDiversity
      + 0.05·reliability
      + 0.15·listingQuality
      + 0.15·recency
```

Components, each normalised to [0, 1]:

- **volume** — `0.5·logNorm(txCount30d) + 0.5·logNorm(volume30d)`, log-scaled
  (cap 1,000,000) so heavy tails do not dominate linearly.
- **buyerDiversity** — `logNorm(buyers30d)` with cap 10,000.
- **reliability** — `0.5` for every merchant in this snapshot. See the note
  below: this is now a property of the data, not of the code.
- **listingQuality** — mean over the merchant's resources of: input schema
  (+1.0), output example (+1.0), description up to +0.8 gated by composite
  quality, service name up to +0.5 gated by specificity, tags up to +0.3 gated
  by taxonomy relevance, icon present +0.15; normalised by 3.75 and clamped
  to 1.
- **recency** — a decay ladder on the most recent activity timestamp:
  <1 day 1.0, <7 days 0.8, <30 days 0.5, <90 days 0.2, else 0.

**Reliability is constant by data, not by code.** Production computes it as the
mean of per-resource `reliabilityScore ?? apiSuccessRate`, falling back to 0.5
when no positive value exists. Measured directly against the source database,
**0 of 42,201 resources carry either column**, so every merchant takes the
fallback. Verified in the snapshot: all 2,252 rows carry exactly 0.5, so the
component contributes nothing to any ranking difference and its share of every
gap decomposition is exactly 0. If either column is ever populated, this
invariant breaks — and it breaks silently.

The weights are the one place the formula encodes a judgement call, which is why
they are exposed as a single editable constant. See the README's "How to
disagree".

### The reference clock

The production code called `Date.now()` for recency. That is right for a live
index and wrong for reproduction: it makes output depend on the day you run it,
so the same input yields different scores on different days.

This repo anchors recency to the snapshot's own `collectedAt`. Live clocks break
determinism; the snapshot timestamp is the only defensible zero point for a
frozen dataset.

## 4. Equivalence test

`npm run verify` recomputes all five score components for every merchant from
raw snapshot fields and compares them against the stored breakdown. Result:

| component | exact matches |
|---|---|
| volumeSignal | 2,252 / 2,252 |
| buyerDiversity | 2,252 / 2,252 |
| reliability | 2,252 / 2,252 |
| listingQuality | 2,252 / 2,252 |
| recency | 2,252 / 2,252 |

**All five components reproduce exactly for every merchant.**
`equivalence.unreproducibleMerchantIds` in `claims.json` is empty, and a
verification transform asserts that it is.

The July edition of this study carried a known reproduction gap: recency
reproduced for 1,127 of 1,132 merchants, because that collector serialized only
a merchant-level `lastUpdated` and the formula also reads a per-resource one.
The September collector serializes both, so the gap does not arise. The same
fix applies to `iconUrl`, which the current listing-quality term reads and the
earlier collector did not emit.

## 5. Pass 1 — concentration and decomposition

`scripts/analyze.ts`. Gini and HHI are computed over 30-day transaction counts
per category. Quartiles are cut by `rankPosition` ascending, with
`qSize = ceil(n/4)`, so the final quartile absorbs the remainder and can be
smaller than the others (Data & Enrichment: 23/23/23/22).

Gap decomposition attributes the Q1−Q4 mean-score difference to components:
`share_c = (Q1_c − Q4_c) × weight_c / gap`. Shares are reported to four
decimals; because reliability is constant its share is exactly 0 in every
category.

The cold-start ceiling is the maximum score a merchant with no transaction
history can reach: `0.05×0.5 + 0.15×1.0 + 0.15×1.0 = 0.3250`, with volume and
buyerDiversity necessarily 0. It depends only on the weights, so it is identical
across categories.

Note what the ceiling arithmetic implies about the reliability term. A merchant
already receives `0.05 × 0.5 = 0.025` from the constant. Populating the slot
with a perfect uptime signal raises it to `0.05 × 1.0 = 0.050`, an increment of
**0.025** — smaller than the smallest gap in the study by an order of magnitude.

## 6. Pass 2 — the formula-independent re-cut

`scripts/recut.ts`. Pass 1 can only speak in the formula's own terms. Pass 2
sorts merchants by the rank the index assigned, then measures four raw fields
nobody scored: `hasInputSchema`, `hasOutputExample`, `descriptionLength`,
`tagCount`. If the top quartile were winning on documentation, it would appear
here without any weights involved.

Quartile boundaries are **read from** `data/analysis-results.json`, not
recomputed, so the cut aligns with Pass 1 by construction.

"One merchant, one listing" is itself a choice, and the choice could flatter the
result — so all three defensible rules are emitted:

- **primary** — the merchant's first resource (the figures cited in the report)
- **pooled** — every resource, pooled (multi-listing merchants weigh more)
- **max** — one row per merchant, best value per field

**The direction does not hold on every axis, and that is recorded rather than
smoothed over.** In Data & Enrichment: input-schema rate is tied at 100% in
every quartile under all three rules; output-example rate favours the *top*
quartile under all three; mean tag count favours the bottom quartile under all
three; and mean description length favours the bottom quartile under the
primary and pooled rules but the top quartile under `max`.

`recut.robustness.directionHoldsUnderAllRules` is therefore asserted as a claim
with the value **`false`**, and `verify.ts` checks it rather than asking the
reader to trust a summary.

## 7. Known limitations

- **Market scale.** Total 30-day volume across the four analysed categories is
  ~$38,735. Concentration measures over a market this small are real but
  fragile: a handful of merchants moves them. These are early-market findings.
- **Author participation.** The author's service is in the excluded "Other"
  bucket and contributes to no analysed statistic. See §2.
- **Reliability is inert.** At a constant 0.5 the component cannot differentiate
  anyone. Any claim about its 0.05 weight is a claim about a placeholder.
- **Single-query probe design.** The CDP probes used one representative query
  per category. A different phrasing would surface a different result set;
  the probes evidence that a specific reasonable query buries specific
  merchants, not a general claim about all queries.
- **No forward projection.** Everything here describes one instant,
  2026-09-09. Nothing forecasts how concentration evolves.
- **Excluded majority.** 1,256 of 2,252 merchants sit in "Other" and are outside
  the analysis entirely.
- **Correlation, not causation.** The data shows documentation quality does not
  track rank position. It does not establish that improving documentation would
  fail to help a specific merchant.

## 7a. One edit to a frozen artifact, disclosed

`data/cdp-probes.json` had four annotation keys renamed before publication:
`decipherRank` → `referenceRank`, `decipherScore` → `referenceScore`,
`decipherListingQ` → `referenceListingQ`, `decipherTxCount30d` →
`referenceTxCount30d` (132 keys in total).

These are labels this study's serializer wrote when recording each probe result,
not data the probed endpoint returned. The endpoint's response — result
positions, counts and search method — is the evidence and is untouched; every
value in the file is byte-identical to the 2026-07-25 run that produced it.

That file is the **July** probe record, retained unchanged. The probe run
matching this snapshot is `data/probes-2026-09-09.json`. Both are published.

The same rule is why the merchant URLs in `data/raw-data.json` that point at the
author's service were **not** touched: those are catalog content returned by a
third party, so changing them would be falsifying evidence.

## 8. External figures

The ERC-8004 figures cited in the report (~34,000 registrations, 224 live
endpoints; YS Hwang, ETHGlobal NY, June 2026) are **reported by a third party**
and are not measured here. They appear in `claims.json` marked
`"source": "external"`, and `verify.ts` labels them as unverified rather than
passing them silently.

## 9. Reproducing

```bash
npm install
npm run all      # analyze -> recut -> verify
```

No configuration, no database, no network. `npm run analyze` regenerates
`data/analysis-results.json` byte-for-byte identically to the committed copy;
re-running any script produces identical output, since no timestamps, random
seeds or locale-dependent sorting reach the emitted JSON.

`npm run probe` is the exception: it is optional, it touches the network, and it
is non-deterministic by nature. See the README.

The report's figures are rendered by a separate matplotlib set that is not
published in this repository. Every value they display is read from the
artifacts above at render time, so each one can be checked against
`analysis-results.json` without the plotting code.
